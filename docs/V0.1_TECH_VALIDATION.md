# CAN-X V0.1 Technology Validation Design

> **Status**: Active implementation design  
> **Date**: 2026-09-15  
> **Sources of truth**: `PRD.md`, `SPEC.md`, `AGENTS.md`  
> **Validation environment**: Windows; synthetic CAN only; no physical CAN hardware; no macOS host

## 1. Purpose and decision

V0.1 validates one bounded vertical slice:

```text
VirtualAdapter
→ Python CAN Runtime
→ Capture / normalize / bounded fan-out
├─ Recorder
├─ Metrics
└─ binary MessagePack stream
   → Web Worker
   → bounded view buffer
   ├─ virtualized Trace
   └─ downsampled Plot

Deterministic mock Agent
→ ToolRegistry
→ trace.summary
→ Runtime-owned captured data
→ structured result
```

Three implementation orders were considered:

1. Runtime-first: easiest headless testing, but delays proof of the desktop boundary.
2. Desktop-first: gives early visual feedback, but risks building a shell around an unproven data path.
3. Thin vertical increments: bootstrap both process boundaries, then grow the runtime-to-UI path one independently tested step at a time.

V0.1 uses option 3 and follows the mandated Step 1–17 order. Each step must leave a testable increment; no step may claim hardware, macOS, Python 3.13, or performance validation without evidence from that environment.

## 2. Scope

### In scope

- Tauri 2 desktop shell and explicit Python sidecar lifecycle.
- React 19, TypeScript, Vite, Dockview, Zustand, TanStack Query, TanStack Virtual, i18next, and an ECharts canvas plot.
- Headless Python runtime with FastAPI control endpoints.
- Formal `Frame` and `FrameBatch` domain schemas.
- Deterministic multi-channel Classic CAN and CAN FD `VirtualAdapter`.
- Capture, timestamp normalization, bounded fan-out, recorder, metrics, and binary MessagePack WebSocket streaming.
- Web Worker decoding, bounded frontend storage, virtualized Trace with follow/freeze, and one downsampled live plot.
- Read-only `ToolRegistry`, `ToolDefinition`, `ToolExecutor`, and `trace.summary`.
- Reproducible synthetic benchmark runner and a factual V0.1 validation report.

### Out of scope

- Physical Vector, PCAN, Kvaser, ZLG, Panda, SocketCAN, or other adapter validation.
- CAN transmission, ECU mutation, a production TX safety workflow, and hardware-in-the-loop tests.
- Full DBC editor, ISO-TP, UDS, J1939, DoIP, XCP, replay, flashing, fuzzing, or diagnostics.
- Full scripting IDE, arbitrary-code sandbox, planner, multi-agent runtime, memory system, cloud, accounts, licensing, collaboration, or public plugin SDK.
- Production Parquet/DuckDB storage and a complete project format. V0.1 must preserve their future boundaries but need not implement them.
- macOS real-machine validation and claims of Python 3.13 compatibility without a Python 3.13 test run.

## 4. Process and lifecycle model

V0.1 has two required processes:

- **Tauri Desktop** owns the application window and the child-process lifecycle.
- **Python CAN Runtime** owns CAN data, capture, recorder, metrics, tools, HTTP, and WebSocket services. It can start headlessly without Tauri.

Lifecycle contract:

1. Tauri reserves or receives a loopback endpoint and starts the packaged runtime sidecar with an explicit session token and parent-process identifier.
2. Tauri polls `GET /health` with a bounded startup deadline before declaring the runtime ready.
3. The runtime reports `starting`, `ready`, `stopping`, or `failed` through `GET /runtime/status`; the UI renders these states but does not control process internals.
4. An unexpected child exit is detected through the sidecar exit event. V0.1 exposes `unavailable` and a manual bounded restart; it does not implement an unbounded restart loop.
5. Normal desktop exit calls a shutdown command that requests `POST /runtime/shutdown`, waits for a bounded grace period, then terminates only the owned child if necessary.
6. The runtime handles shutdown by refusing new capture starts, stopping capture, flushing recorder work, closing stream clients, and exiting.
7. `canx-runtime` remains directly executable for tests, CLI use, and future remote/headless operation.

Only loopback binding is in scope. Authentication is a per-process ephemeral token; secrets are not logged.

## 5. Domain schemas

### 5.1 Frame

| Field | Type | Rule |
|---|---|---|
| `sequence` | unsigned 64-bit logical integer | Monotonic within one capture stream. Encoded as a MessagePack integer. |
| `channel_id` | non-empty UTF-8 string | Stable adapter channel identity. |
| `arbitration_id` | unsigned 32-bit logical integer | `0..0x7FF` for standard; `0..0x1FFFFFFF` for extended. |
| `is_extended` | boolean | Selects arbitration-ID range. |
| `is_fd` | boolean | Enables CAN FD payload rules. |
| `bitrate_switch` | boolean | Must be false for Classic CAN. |
| `error_state_indicator` | boolean | Must be false for Classic CAN. |
| `dlc` | unsigned 8-bit logical integer | Payload length in bytes for the normalized V0.1 schema: `0..8` Classic, allowed CAN FD lengths `0..8,12,16,20,24,32,48,64`. |
| `data` | bytes | Length must equal `dlc`; binary in MessagePack. |
| `direction` | enum `rx`, `tx` | Virtual capture generates `rx`; future `tx` does not imply authorization. |
| `hardware_timestamp` | optional float64 seconds | Adapter clock value when available. |
| `host_timestamp` | float64 seconds | Host monotonic capture time. |
| `normalized_timestamp` | float64 seconds | Stream-relative monotonic time used for ordering and display. |
| `clock_domain` | non-empty UTF-8 string | Identifies the source clock, for example `host.monotonic`. |
| `timestamp_quality` | enum `hardware`, `host`, `estimated` | Describes normalization source quality. |
| `flags` | unsigned 32-bit bit set | Reserved transport/domain flags; unknown bits are preserved. |

The Python domain model is immutable and independent of FastAPI, pandas, React, and Tauri. Cross-boundary schemas derive from the runtime contract rather than an independently invented UI shape.

### 5.2 FrameBatch

| Field | Type | Rule |
|---|---|---|
| `schema_version` | unsigned integer | Starts at `1`. |
| `stream_id` | UUID string | Changes for each capture stream. |
| `first_sequence` | unsigned 64-bit logical integer | Equal to the first frame sequence. |
| `last_sequence` | unsigned 64-bit logical integer | Equal to the last frame sequence. |
| `frame_count` | unsigned integer | Equal to `len(frames)`. |
| `frames` | array of `Frame` | Non-empty and strictly contiguous for a generated batch. |

Batch size is runtime configuration, not part of the protocol contract. Benchmarks compare 50, 100, 250, 500, and 1000 frames per batch.

## 6. Capture pipeline and pressure policy

```text
VirtualAdapter.recv
→ CaptureWorker
→ TimestampNormalizer
→ bounded ingress buffer
→ independent bounded subscriber queues
   ├─ Recorder consumer
   ├─ Metrics consumer
   └─ StreamPublisher consumer
```

- Capture does not call UI or recorder code directly.
- Recorder and stream publisher are sibling consumers.
- Sequence is assigned once at capture ingress. Every loss is observable as an explicit dropped counter or downstream sequence gap.
- V0.1 uses bounded queues. A slow UI client may lose stream batches after the stream queue reaches its explicit limit; capture and recorder continue. The dropped-stream count is observable.
- Recorder pressure is not silently discarded. Recorder enqueue timeout or write failure transitions the recorder to a structured failure state and is surfaced in metrics/API. V0.1 synthetic tests size queues to prove normal-load integrity, not to claim infinite backpressure capacity.
- Capture stop is ordered: stop adapter input, drain/close consumers, flush recorder, publish final metrics, then close the stream.

## 7. Recorder boundary

The V0.1 recorder writes an append-only, chunked MessagePack capture format to a session-owned temporary or configured project path. Each chunk contains schema version, stream ID, sequence bounds, and frames. Atomic file replacement is not required because the format is append-only, but open/write/flush/close failures must be reported.

This format is a prototype transport-neutral evidence format, not the long-term large-data architecture. Parquet remains the planned large-dataset store; SQLite remains metadata only.

## 8. IPC and API

### 8.1 Control plane: HTTP/JSON

Minimum V0.1 routes:

- `GET /health` — process liveness and schema version.
- `GET /runtime/status` — lifecycle and active capture summary.
- `POST /capture/start` — validate virtual configuration and start one capture session.
- `POST /capture/stop` — idempotently stop the active session and flush consumers.
- `GET /metrics` — current metrics snapshot.
- `POST /tools/execute` — execute a registered tool after runtime-side risk and permission checks.
- `POST /runtime/shutdown` — authenticated loopback lifecycle request used by the owning desktop process.

Errors use:

```json
{
  "code": "capture.already_running",
  "message": "Capture is already running.",
  "details": {},
  "recoverable": true,
  "source": "runtime"
}
```

### 8.2 Data plane: binary WebSocket

- `GET ws://127.0.0.1:<port>/stream/frames`
- Every application message is a binary MessagePack `FrameBatch`.
- Text frame payloads are rejected with a structured close reason.
- Clients joining mid-stream receive future batches only. History uses future query/storage APIs, never high-frequency `GET /frames` polling.
- Disconnecting or freezing a client does not stop capture or recorder work.

## 9. Runtime metrics

Metrics are monotonic counters plus interval gauges:

- `generated_frames`, `captured_frames`, `recorded_frames`, `streamed_frames`
- `sequence_gaps`, `dropped_frames`, `dropped_stream_frames`
- `capture_rate`, `record_rate`, `stream_rate` in frames/second over a documented rolling interval
- `ingress_queue_depth`, `recorder_queue_depth`, `stream_queue_depth`
- `memory_usage_bytes`, `runtime_cpu_percent`
- `uptime_seconds`, `active_channels`, `recorder_state`

Counter ownership is explicit: the adapter increments generated; capture increments captured; recorder increments only after successful append; stream increments after a batch is handed to the WebSocket layer. Operating-system CPU and memory measurements are best effort and must report unavailable rather than fabricate zero.

## 10. Frontend data path

```text
binary WebSocket
→ dedicated Web Worker MessagePack decode
→ worker-owned bounded ring buffer
→ throttled immutable viewport snapshots
├─ TanStack Virtual Trace rows
└─ downsampled ECharts series
```

- React state stores UI controls, connection state, metrics snapshots, and only the current bounded viewport snapshot.
- No per-frame `setState` and no complete capture history is stored in React or Zustand.
- Follow mode advances the viewport at a governed refresh rate. Freeze mode stops viewport snapshots while the worker continues bounded ingestion and reports dropped view frames if its view buffer wraps.
- Trace columns are Timestamp, Channel, ID, DLC, Data, and Direction.
- Plot consumes a renderer-neutral series interface. V0.1 derives one deterministic byte value and applies bounded downsampling before ECharts.

## 11. Performance governor

The minimum governor observes worker backlog, stream lag, render duration, and runtime pressure. It has three levels:

- `normal`: configured Trace and Plot refresh rates; restrained compositor-only animation.
- `reduced`: lower Trace refresh, stronger Plot downsampling, disable decorative animation.
- `critical`: freeze nonessential Plot refresh and minimize Trace refresh while preserving controls and status.

The governor never changes capture, recorder, timestamps, permission checks, or audit behavior. Thresholds are configuration and benchmark outputs, not permanent protocol constants.

## 12. Agent tool boundary

Every `ToolDefinition` contains `name`, `description`, `input_schema`, `output_schema`, `risk_level`, `permissions`, `timeout_seconds`, and `idempotency`. `ToolExecutor` looks up an allow-listed definition and enforces risk/permission policy inside the runtime.

V0.1 registers only read-only `trace.summary`. Its input contains `start_time`, `end_time`, optional `channel_id`, and optional `arbitration_id`. Its output contains `frame_count`, `unique_ids`, ordered `top_ids`, `frame_rate`, and the effective `time_range`. Invalid ranges return a structured error. The deterministic mock Agent may request this tool but cannot register arbitrary Python functions or access an adapter.

## 13. Benchmark plan

The reproducible benchmark matrix covers:

- Channels: 1, 4, 8.
- Frame modes: Classic CAN, CAN FD.
- Load profiles: low, medium, high synthetic load.
- Batch sizes: 50, 100, 250, 500, 1000.

Each run records seed, environment, dependency versions, duration, workload configuration, generated/captured/recorded/streamed counts, detected gaps, queue peaks, runtime and desktop CPU when available, memory, disk throughput, stream latency, Trace render latency, and Plot update latency.

Rules:

- A warm-up and measured interval are separate.
- Runtime-only benchmarks are distinct from desktop end-to-end benchmarks.
- UI freeze/slow-consumer cases verify recorder independence.
- Results are written as raw machine-readable output plus a summarized table.
- Unsupported measurements are recorded as `NOT VERIFIED`, never as zero.
- No threshold is called acceptable until a measured baseline exists.

## 14. Step gates

Each implementation step follows:

```text
expected behavior
→ failing test
→ minimal implementation
→ passing focused test
→ applicable integration/build/lint checks
→ diff and architecture self-review
→ development record update
```

Step 17 creates `docs/V0.1_VALIDATION_REPORT.md` with factual evidence for architecture validation, implemented scope, commands and results, performance, gaps, memory behavior, UI behavior, bottlenecks, recommendations, and Go/No-Go. Real hardware and macOS remain `NOT VERIFIED` in this environment.

## 15. Dependency review

The mandated primary dependencies are established, actively maintained open-source projects under permissive licenses or mixed permissive distributions. Before lockfile creation, exact versions and license metadata must be captured from the resolved package set. Optional/transitive packages with copyleft, commercial, abandoned, or platform-restricted terms block adoption until reviewed.

No legacy CAN-Space or CanLab source is used by this design, so `docs/REUSE_LEDGER.md` is not created at this stage.

## 16. Internal consistency review

- Product scope matches PRD V0.1 and does not add diagnostics, cloud, full replay, or hardware support.
- Process, storage, frame, realtime, safety, and Agent boundaries match SPEC.
- Recorder is parallel to UI streaming; UI pressure cannot own or stop capture.
- The runtime is headless and remains usable without Tauri.
- MessagePack batches contain a formal versioned runtime schema.
- React receives bounded snapshots, not unbounded frame history.
- Only a read-only tool is implemented; no direct TX path exists.
- Benchmarks define measurements but contain no invented result.
- Documentation naming consistency is resolved: `AGENTS.md` is the sole canonical guide filename.
- Current environment limitation: Python 3.12 is available through the Codex runtime, but Python 3.13 and Rust/Cargo are not currently available. Any affected result must remain `NOT VERIFIED` until those tools run.
