# CAN-X V0.1 validation report

> Date: 2026-09-15  
> Host: Windows 11 build 26200  
> Scope: Virtual CAN technology proof only

## Conclusion

**Architecture validated: yes, within the headless Virtual-CAN proof boundary.**

Recommendation: **Conditional Go** for the next small V0.1 engineering increment. The Runtime runs without the UI, capture/recorder/stream are runtime-owned, React receives bounded snapshots, and the Agent reaches data only through an allow-listed read-only tool. This is a **No-Go** for production release, physical CAN claims, macOS claims, or performance thresholds.

## Implemented

- Tauri 2 + React 19 desktop shell with Dockview Trace, Plot, and Agent areas.
- Python 3.13 FastAPI Runtime with health, lifecycle, Virtual CAN capture, batching, binary WebSocket, recorder, metrics, and structured errors.
- Immutable Frame and FrameBatch schemas with sequence and timestamp metadata.
- Worker-owned bounded viewport, virtualized Trace, governed updates, and bounded ECharts series.
- Runtime ToolRegistry/ToolExecutor and the read-only `trace.summary` tool.
- Reproducible runtime-only benchmark and full matrix driver.

## Review corrections

The final independent code review initially returned No-Go and identified three blocking gaps. Before this report was finalized:

- the desktop workspace gained explicit Virtual Capture start/stop control and exact Tauri development/production CORS origins;
- recorder/archive and stream batching became independent sibling consumers, with a regression test proving a deliberately blocked recorder does not delay a stream batch;
- generated and captured counters moved to Adapter/Capture ownership, WebSocket delivery owns `streamed_frames`, stream gaps split batch boundaries safely, and the full matrix was rerun;
- lifecycle operations gained serialization, Runtime lifespan cleanup, failed-session visibility, sidecar restart-after-exit handling, and stronger health identity checks;
- Runtime history and Worker viewport state now reset at capture-session boundaries.

## Integrity and memory behavior

- Recorder is a lossless sibling consumer and was tested with no WebSocket client; recorded and captured counts remained equal.
- Stream clients use independent bounded queues and can drop old UI work without blocking capture or recorder work.
- Runtime query history is bounded to 100,000 Frames.
- Each current panel Worker ring is bounded to 20,000 Frames; React receives a bounded immutable snapshot and does not own capture history.
- Worker snapshots are governed to approximately 33 ms; capture and recorder timing are unaffected.

## UI behavior

Component behavior, strict types, bundle creation, and Tauri compilation are verified. Manual visual interaction, render latency, animation behavior under sustained pressure, and packaged application launch are **NOT VERIFIED**.

The Vite build shows a 362.34 kB lazy DockWorkspace JavaScript chunk plus ECharts-related lazy chunks up to 258.89 kB. This is not a correctness failure, but bundle and first-plot cost should be profiled before expanding Plot.

## Known bottlenecks and limitations

- Trace and Plot currently open separate bounded WebSocket/Worker pipelines. This preserves correctness but duplicates decode and viewport memory; a shared frontend stream store is the next likely optimization.
- Recorder performs one thread-offloaded file write per batch. Long-duration and slow-disk pressure behavior needs soak testing.
- V0.1 does not yet persist an Agent Tool audit log; only the read-only `trace.summary` tool exists. Any future TX or mutation tool remains blocked until the complete approval and audit chain exists.
- The benchmark does not measure end-to-end stream latency, Trace render latency, Plot update latency, desktop CPU, GPU use, or UI responsiveness: **NOT VERIFIED**.
- Physical Vector/PCAN/Kvaser/ZLG hardware, error frames, hardware timestamps, bus-off handling, and transmit policy are **NOT VERIFIED**.
- macOS and packaged installer/sidecar distribution are **NOT VERIFIED**.
- The repository has no CAN-Space/CanLab code reuse; therefore no reuse ledger was required.

## Architecture changes recommended

1. Share one frontend WebSocket/Worker-backed bounded store between Trace and Plot.
2. Add recorder slow-disk/soak tests with explicit backlog and failure metrics.
3. Add an end-to-end desktop benchmark harness before setting UI or latency thresholds.
4. Design packaged Python sidecar distribution and verify it separately; do not change runtime ownership.

## Go / No-Go

- **Go:** continue V0.1 with one coherent increment at a time, starting with the shared frontend stream store or recorder soak validation.
- **No-Go:** production use, real CAN TX, ECU mutation, hardware compatibility statements, macOS compatibility statements, or Rust migration of Python business logic.
