## 1. The defect

The V0.3 baseline shipped a P2 `ACCEPTED NON-BLOCKING` defect:

```text
apps/desktop/src-tauri/tauri.conf.json   build.devUrl = "http://localhost:1420"
apps/desktop/src-tauri/tauri.conf.json   build.beforeDevCommand = "pnpm dev"
apps/desktop/vite.config.ts              (no server configuration at all)
```

The Tauri dev shell polls exactly the URL its `devUrl` names — `localhost:1420`.
But `apps/desktop/vite.config.ts` pinned no port, so Vite bound whatever free
port it found (1420, 1421, …). When it did **not** land on 1420, `pnpm tauri dev`
waited forever on a server it could not reach; and even when it did land on 1420,
a taken port silently pushed Vite to 1421 while Tauri kept polling 1420. The two
configs were free to drift, and nothing detected it.

## 2. The fix (minimal, fail-closed)

`apps/desktop/vite.config.ts` now declares the dev-port contract explicitly:

```ts
server: {
  port: 1420,
  strictPort: true,
},
```

- `port: 1420` makes the Vite dev server bind the exact port Tauri waits on.
- `strictPort: true` makes it **fail closed**: if 1420 is taken, Vite refuses to
  start rather than silently moving to another port — so a misconfiguration
  surfaces as an error instead of as a hung dev shell.

No product architecture, Runtime API, recorder, Plot, Replay, dependency,
lockfile or dev-server-proxy change was made. `beforeDevCommand` and `devUrl`
in `tauri.conf.json` were left byte-identical.

## 3. Regression guard

`apps/desktop/src/smoke/dev-port-contract.test.ts` locks the contract so the two
configs can never drift again. It reads the **real** configs, not source text:

- the Vite config as the module Vite itself loads (`import viteConfig from
  "../../vite.config"`), so a comment that merely mentions `1420` cannot satisfy
  it; and
- the Tauri config as parsed JSON, re-deriving the port with the WHATWG `URL`
  parser rather than asserting a literal string.

It asserts three things:

```text
Tauri devUrl port          == 1420
Vite server.port           == Tauri devUrl port
Vite server.strictPort     === true
```

## 4. RED → GREEN

The guard was written to fail against the pre-fix configuration, and the fix was
then restored. The RED run used the original `vite.config.ts` (checked out from
the base with `git show`, the working fix preserved aside and restored after):

```text
RED   (original vite.config.ts, no server block)  2 failed | 1 passed
      expect(viteConfig.server?.port).toBe(1420)          -> undefined
      expect(viteConfig.server?.strictPort).toBe(true)    -> undefined
GREEN (port: 1420, strictPort: true)              3 passed
```

The third case (the Tauri `devUrl` is 1420) passes in both runs, which is
correct: that half of the contract was never the broken one.

## 6. Dev-server evidence (what the native smoke could prove here)

The task's §5.4 asks for a real `pnpm tauri dev` run. **The full native smoke is
NOT VERIFIED in this environment**, because:

- `pnpm` is not on `PATH` (and `corepack` is absent), so `pnpm tauri dev` cannot
  be invoked, and `tauri.conf.json`'s `beforeDevCommand` is `pnpm dev`;
- there is no interactive desktop session in which the Tauri window could be
  created and observed.

`beforeDevCommand` and `devUrl` live in `tauri.conf.json`, which this task's
ownership surface forbids editing, so the harness could not be sidestepped
either. What **was** run, against the real Vite config with the local binary:

```text
vite (no flags, reads vite.config.ts)
  -> "VITE v8.3.0 ready"
  -> "Local: http://localhost:1420/"          # binds the declared port

vite (second instance, 1420 already held)
  -> exit 1, "Error: Port 1420 is already in use"
  -> refuses to start; does NOT fall back to 1421   # strictPort fail-closed
```

That verifies the two facts the defect was about — Vite binds 1420, and it fails
closed rather than drifting. It does **not** verify Tauri window creation, the
Runtime sidecar start, `/health` and `/runtime/status` reachability, the WebView
load, or the shutdown-without-orphan behaviour; those require a real
`pnpm tauri dev` and are recorded here as NOT VERIFIED, not as passed.
