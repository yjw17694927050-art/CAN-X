## 1. Phase objective

Establish the Desktop-side **Project Open boundary / foundation**: from a user-chosen project
directory, through the trusted native Tauri boundary and a typed TypeScript desktop bridge,
through project-open orchestration, to the Desktop Runtime project client and the canonical
Runtime read model.

```text
user selects CAN-X project directory
        ↓
trusted native Tauri boundary        select_project_directory   (Rust)
        ↓
typed TypeScript desktop bridge      selectProjectDirectory()   (src/desktop)
        ↓
project-open orchestration           openProjectFromNativeDialog(selectDirectory, inspectProject)
        ↓
Desktop Runtime project client       inspectProject(projectPath) (src/runtime)
        ↓
GET /project/inspect?project_path=…
        ↓
canonical Project read model { projectId, displayName, schemaVersion, createdAt, updatedAt }
```

This phase establishes the **boundary and its foundation**. It does not build a Project UI.

### 2.1 The Runtime client (`V0.3-12-A`)

`inspectProject(projectPath)` calls `GET /project/inspect?project_path=…` and projects the
Runtime's `snake_case` wire shape onto the Desktop's camelCase read model — in that boundary
and nowhere else.

Five properties are load-bearing, and each is covered by a test:

- **A project is named, never remembered.** `projectPath` is an argument on every call; there
  is no module-level path, no store, no `setCurrentProject`, no cached handle.
- **The path is forwarded, not interpreted.** No `resolve`, `expanduser`, `lower`, separator
  rewrite or trim. It is encoded with `URLSearchParams`, so the whole path — spaces, `?`, `&`,
  `#`, `/`, `%` — is one query value and never structure.
- **Every response is validated, never asserted.** Each of the five declared fields is checked
  and a fresh object is built from exactly those five; a missing field, a wrong type, an array
  where an object was declared all refuse the whole payload. There is no cast.
- **Three typed errors stay distinguishable.** `RuntimeProjectApiError` (the shared five-field
  envelope `code`/`message`/`details`/`recoverable`/`source` preserved intact, plus the HTTP
  status), `RuntimeProjectTransportError` (fetch rejected, or a non-2xx answer that is not the
  shared envelope), `RuntimeProjectContractError` (a 2xx payload the contract does not describe).
- **A diagnostic never echoes the request.** Every message this layer authors is a static
  constant; neither error type has a field a path, a URL or a response body could leak into.

### 2.2 The native directory bridge (`V0.3-12-B`)

One new Tauri command, `select_project_directory`. Cancel resolves to `Ok(None)`; a selection
resolves to `Ok(Some(path))`.

- **Zero caller-supplied filesystem arguments.** The command's only parameter is the
  Tauri-injected `app: AppHandle<R>`. There is no `path`, `directory` or `project_path` for a
  renderer to populate, and a regression test asserts the parameter list literally.
- **Rust does not judge the selection.** No `project.json`, no `project.db`, no schema check,
  no identity check, no `ProjectService` logic — the module's own source is asserted to contain
  none of the fingerprints of a project-identity check. Project authority stays with the Python
  Runtime `ProjectService`. The selected directory path *is* allowed to return to the renderer,
  because `project_path` is already the explicit input of the Runtime's `GET /project/inspect`
  contract — but the bridge never decides whether the directory is a project.
- **Every failure is a declared typed code with static text**, and no error serialization
  carries the selected directory (asserted with a distinctive `secret-program` marker in the
  fixture path, and by asserting the error object has exactly the three declared keys).
- **No side channel.** The absence of `println!`/`eprintln!`/`dbg!`/`log::*`/`.emit(`/tracing
  is asserted, so the return value is the only thing this bridge publishes.
- **No dependency.** `Cargo.toml`, `Cargo.lock` and `capabilities/default.json` are untouched;
  the existing `tauri_plugin_dialog` directory picker is reused.

### 2.3 The TypeScript bridge and the orchestration (`V0.3-12-C`)

`selectProjectDirectory(): Promise<string | null>` invokes the command named
`select_project_directory` with **no caller arguments**, resolves `null` on cancel, passes a
native structured rejection through as a typed `ProjectDirectoryBridgeError`, and reports a
malformed successful IPC payload as a plain contract `Error`. It reads no project definition,
touches no filesystem API and keeps no module-level state.

`openProjectFromNativeDialog(selectDirectory, inspectProject)` composes the two boundaries. Both
come in **by injection** and the project read model stays a **generic type parameter**, so the
module names neither the Runtime client nor a duplicated copy of the Runtime project schema —
which is also what kept it parallel-safe while V0.3-12-A was being written concurrently. Cancel
returns `{ status: "cancelled" }` before any inspection; otherwise the selected path is forwarded
character for character and the outcome is `{ status: "opened", projectPath, project }`. No path
normalisation, no global current project, no persistent state, no DBC coupling, no error
translation.

### 2.4 Cross-boundary integration

`apps/desktop/src/orchestration/project-open.integration.test.ts` instantiates the **real**
bridge, the **real** orchestration and the **real** Runtime client, and stubs only the two outer
adapters — the Tauri `invoke` and `fetch`. It proves the whole chain, plus the Rust/TS
command-name identity (§4). The native dialog is deliberately **not** automated: the OS
selection edge is proved by the Rust module's focused tests.

## 5. The AGENT-02 pilot — what was actually run

This is the first **real** AGENT-02 pilot. It ran **1 Main Agent + 3 native Tianshu workers**,
not the `1 + 2` the earlier design assumed.

### 5.1 Why three, and why nothing was reconfigured

Tianshu's native default worker concurrency is **3**. The pilot's purpose is to validate the
**native default**, so the Harness concurrency configuration was **not** touched:

```text
effective maxWorkers           3
concurrency config modified    NO   (Tianshu source, desktop runtime,
                                     RIVET_MAX_WORKERS and workers.maxWorkers
                                     are all unchanged)
/team (native multi-worker dispatch)   USED
```

The three workers were dispatched in **one native parallel batch**, and their three
TaskContracts were verified conflict-free by CAN-X *before* dispatch (§5.3).

### 5.4 Filesystem isolation — measured, not assumed

```text
Filesystem mode:  SHARED WORKTREE
```

Evidence: throughout the 389-second window `git worktree list` returned a **constant set of 5
worktrees** — the repository root on the feature branch plus four pre-existing worktrees from
earlier sessions — and **no new worktree or branch appeared**. All three workers' artifacts
appeared in the **same** `git status --porcelain` of the **same** working tree, on the **same**
branch the Main Agent had checked out. Every one of the 151 samples classifies as shared;
none as isolated.

This is the fact `AGENT_02_PILOT_PLAN.md` §6 said the pilot had to *measure* rather than derive
from shipped runtime text, and it is the first entry of that observation.

**Policy consequence (already decided, and it held).** Ownership was enforced by policy, not by
the filesystem: the TaskContract's `allowed_paths` plus Git-derived
`history_touched_paths` is the enforcement, and the C0/disjoint pair selection is what made a
shared worktree safe. No two workers ever wrote the same file (§5.5), so the STOP condition of
the shared-worktree policy was never reached.

### 5.6 Native result → CAN-X validation

Each native worker returned a structured envelope (`status`, `summary`, `changedFiles`,
`findings`, `tests`, `risks`, `nextActions`, `evidenceStatus`). Those envelopes are **reports**,
not authority. The Main Agent re-derived every claim that mattered from the repository:

```text
worker self-report  ≠  Git evidence      →  Git evidence is the authority
```

- The three worker `changedFiles` lists were cross-checked against `history_touched_paths`
  (§5.5) — they agree, so the earlier "changedFiles" discrepancy in the raw envelopes (one
  worker echoed absolute Windows paths alongside the relative ones) did not change the
  conclusion.
- Each worker's focused test claim was **re-run by the Main Agent** (§6), not accepted.
- One worker's evidence was **misleading and was discarded**: worker A reported `pnpm test`
  passing but its first full-suite run had failed on an unrelated realtime-panel timeout, and
  it explained the difference by creating a `pnpm` shim outside the repository. The Main Agent
  re-ran the same suite directly (§6) rather than adopting the explanation.
- Worker B's declared conflict between *acceptance criterion 5* and *requirement 2* of its own
  contract was a **contract wording defect of the Main Agent's**: the criterion read "no
  published payload or error contains the selected directory path", while the successful
  payload *is* that path. The worker resolved it by interpretation (refusals never carry the
  path; the selection itself is the published value) and said so. The interpretation is the
  correct one and is what the tests pin — **recorded as a defect in the brief, not in the code.**

### 5.7 Context isolation

```text
Context isolation:  PARTIAL
```

Each worker was handed **only its own TaskContract brief** — objective, allowed and forbidden
paths, required tests, handoff requirements — plus the shared repository it must not exceed.
No Main-Agent conversation history, no other worker's task, and no full-project dump was passed
to any worker; the three briefs were disjoint by construction, and the returned results show
each worker confining itself to its own surface (each one edited only its own `allowed_paths`,
and worker C explicitly declined to import the Runtime client whose file was being written
concurrently).

It is nevertheless recorded as **PARTIAL**, not YES: the exact prompt the Harness assembled for
each worker is not directly observable from this session, so "the worker received exactly the
brief and nothing else" is supported by the dispatch construction and by the observed
behaviour, not by direct inspection of the worker prompt.

### 5.8 Did the Main Agent implement the worker bodies?

**No.** The Main Agent wrote the three TaskContracts, ran the CAN-X preflight, dispatched, and
then performed **integration and validation only**: the cross-boundary integration test, the
governance verification, the regression runs, the commits and this documentation. It did not
author, edit or "fix up" any of the three modules' implementation or their unit tests.

### 5.9 One cross-cutting defect the pilot surfaced

`apps/desktop/src-tauri/src/dbc_file_bridge/tests.rs` asserts the crate's **exact** registered
command surface. Registering any new Tauri command therefore turns that regression **RED** —
a hidden coupling between the new bridge and an existing test that no single worker's own
surface reveals, and the reason V0.3-12-B's contract deliberately included that file.

It was resolved by **extending** the invariant, not weakening it: the expected surface names the
new command, `crate_source()` learned the new module, and the no-caller-path scan was extended
to `project_directory_bridge.rs` with the inspected-command count raised 3 → 4 — so the **new**
command is covered by the same invariant every first-party command already was.

### 5.10 Pilot failure policy

No worker FAILED, so the retry policy was not exercised. Two of the three workers (A and C)
were returned by the Harness with a `blocked` envelope rather than `passed`, not because of a
failure condition but because the Harness's own write gate could not complete a scoped `tsc`
(`tsc did not run to completion`); their own focused suites were green, and the Main Agent
re-ran the full frontend gate independently (§6). This is recorded as an **environment
artefact of the harness gate**, not as a worker failure, and it is **not** counted as the
pilot's verification — the Main Agent's own runs are.
