## 1. Phase objective

Make the V0.3-12 foundation reachable by a user, and establish workspace-scoped Project / DBC
Decode Binding state. The phase merges three increments that were originally planned separately —
Project Picker / Project Open UI, DBC Import UI, and DBC Selection / Channel ↔ DBC Binding — into
one product-wiring increment.

```text
启动 CAN-X → Open Project → native directory picker → Runtime inspect
  → Workspace shows the opened project
  → DBC Workspace → Import DBC → native .dbc picker → imported into that project
  → asset list auto-refreshes → browse message / signal
  → select a CAN channel → explicitly bind a project-owned DBC asset
  → the workspace shows that Decode Binding
```

## 3. Scope implemented

### 3.1 Workspace Session

```text
one WorkspaceSessionStore per mounted workspace
the SAME store instance injected into every Dockview React root
no Runtime/global currentProject
no global active DBC
```

`WorkspaceSessionStore` (`apps/desktop/src/workspace/session.ts`) holds `openedProject`,
`channelId -> assetId` decode bindings, the browse selection, and a signal selection reserved for
V0.3-14. It is **not** a Runtime authority: the Runtime stays stateless with `project_path` an
explicit argument on every request, and this store holds no copy of anything the Runtime owns.

It is created by `DockWorkspace` (`useState(createWorkspaceSession)`) and handed to each panel root
through `WorkspaceSessionProvider` — the same way the app's one `QueryClient` already crosses the
Dockview `createRoot` boundary. There is no module-level instance.

**Project switching** — `openProject` *replaces* the session:

```text
old dbcBindings        cleared
old browsedAssetId     cleared
selectedSignal         cleared
same-path reopen       clears too
```

Clearing is unconditional rather than conditioned on the path string changing: a different project
can occupy a path that once held another, and a store that cannot tell those apart must not carry a
selection across the ambiguity.

### 3.2 Project Open

```text
ProjectControls is the production caller
it reuses: selectProjectDirectory · inspectProject · openProjectFromNativeDialog
cancel has no session mutation
typed bridge / Runtime error classification preserved
the selected project filesystem path is NOT rendered
```

`ProjectControls` performs no `fetch`, no direct `invoke` and no filesystem call of its own; a test
asserts that with a `fetch` spy. Four failure classes — `ProjectDirectoryBridgeError`,
`RuntimeProjectApiError`, `RuntimeProjectTransportError`, `RuntimeProjectContractError` — each map
to a distinct human message, and only the Runtime API failure surfaces its stable code.

### 3.3 DBC Import

```text
DbcImportControl is the production caller
it reuses: importDbcFromNativeDialog(projectPath)
success invalidates exactly: ["dbc", "assets", projectPath]
cancel invalidates nothing
no duplicated picker / Base64 / parser / fetch logic
```

The invalidation uses the **exact** key tuple the DBC workspace reads, so the asset list refetches
from the Runtime and the new asset appears without this component knowing the cache's shape.

### 3.4 Channel ↔ DBC binding

```text
explicit channelId -> assetId
session-scoped only
browse selection ≠ decode binding
Bind is the only bind action
Unbind is the only unbind action
the binding candidate asset must be present in the current project's asset collection
the channel list comes from observed RuntimeFrame.channelId
no channel registry / device manager / TX capability introduced
```

`WorkspaceSessionStore.browseAsset` changes only `browsedAssetId` and `assetForChannel()` answers
from the binding map alone, so "the user clicked an asset" cannot re-target a channel's decoder.
`bindChannel` refuses when no project is open, which is why no binding can exist with no project
behind it.

The channel list is the **observed** projection of `RuntimeFrame.channelId` — de-duplicated,
code-unit ordered, blank ids filtered — the only channel identity CAN-X has. No CAN-channel
registry, device manager, channel configuration subsystem or TX capability was introduced.

Binding is **not** persisted: no SQLite migration, no Runtime API, no schema change.

### 3.5 Realtime

```text
project switching does not rebuild DockWorkspace
the existing realtime store remains shared
DbcBindingControl adds a subscriber to the shared store
  but does not create another Worker/WebSocket pipeline
```

The invariant is **one realtime pipeline**, not "one consumer": `DbcBindingControl` *is* an
additional subscriber to the one shared `RealtimeStreamStore`. What it must not do — and does not —
is construct a second `RealtimeStreamStore`, Worker or WebSocket.

The Dockview layout's dependency array no longer contains the project. It previously did, so every
project change disposed and rebuilt the entire layout — and the Trace/Plot roots holding the
realtime subscription with it.

## 6. Known limitations / NOT VERIFIED

```text
Real Dockview panel body E2E under jsdom                 NOT VERIFIED
Real OS project picker E2E                               NOT VERIFIED
Live Tauri IPC shell E2E                                 NOT VERIFIED
macOS / Linux                                            NOT VERIFIED — CI is windows-latest only
real CAN hardware                                        NOT VERIFIED
visual / pixel-level rendering of the new panels         NOT VERIFIED
```

**Dockview panel body E2E — NOT VERIFIED.** Dockview mounts a panel body lazily behind real layout
and jsdom performs no layout, so a Dockview panel's content is not in the document under test. The
integration tests reproduce the exact provider composition `DockWorkspace` injects into each panel
root, and pin Dockview's own contribution by source-level assertions. They do **not** claim real
Dockview layout end-to-end.

**Inactive-channel binding visibility — DEFERRED.** A bound channel that is no longer represented
in the current observed realtime viewport can disappear from the binding table while the session
binding still exists. The binding is therefore not UI-removable until the channel appears again, or
a project switch clears it. This is a deliberate design decision — folding the binding key set into
the channel list would make the binding map itself a channel source, which is the registry SPEC
forbids — and it is **not** fixed.

Also carried, unchanged by this phase: `dbc/`-as-symlink rejection is skipped on Windows; the DBC
registry and filesystem cannot form a single transaction; DBC client-side validation is
contract-shape validation, not a domain-semantics replica; the near-limit Desktop HTTP
serialization cost recorded in V0.3-08 remains; timestamp segment pruning remains disabled.
