## 1. Phase objective

Give CAN-X Desktop a **production-visible, project-scoped, read-only DBC workspace**: an
existing DBC Runtime read model, reached through the already-accepted typed Desktop client,
rendered as a real Dockview panel with asset selection and message / signal inspection.

```text
Future Project Context
        │  explicit projectPath (a prop, never a global)
        ▼
DBC Workspace UI (Dockview panel "DBC")
        ├── listDbcAssets(projectPath)              → asset browser
        └── getDbcDatabase(projectPath, assetId)    → message / signal viewer
                 ▼
        existing Runtime HTTP API  (unchanged)
                 ▼
        Python DBC Runtime authority
```

Not in scope, and not built: a DBC editor, an active DBC, channel ↔ DBC binding, live
decoding, a project picker, an import button.

## 2. Scope implemented

- A real `DBC` Dockview panel, added to the production layout as a sibling tab of `Trace`
  (Dockview 8.3.1 `position: { direction: "within", referencePanel: "trace" }`).
- A project-scoped `DbcWorkspace` component with the explicit interface
  `{ projectPath: string | null }`.
- Read-only asset browsing: `sourceName`, `sizeBytes`, `encoding`, `importedAt` per asset,
  with the `assetId` used only as an internal selection identity.
- Read-only database inspection: version / message count / node count summary, a virtualized
  message list (name, frame id, standard-vs-extended, Classic CAN-vs-CAN FD, length), a
  message detail (senders, cycle time, signal count, comment) and a full signal definition
  table (start bit, length, byte order, signed/unsigned/float, factor, offset, min, max,
  unit, receivers, multiplexing, choices, comment).
- Formal loading / empty / no-project / failure states, each with retry where retry means
  something.
- Full `en` + `zh-CN` i18n for every new user-facing string (~55 keys).
- A negative-space guarantee: the production bundle contains the DBC UI but no test fixture,
  no demo DBC and no mock Runtime response.

## 3. Scope explicitly deferred

Unchanged from the phase brief: DBC import button, project picker, project create/open UI,
drag & drop, multi-file import, DBC editor / rename / delete / replace, active DBC, global
current project, channel ↔ DBC binding, Trace decoded-signal columns, live decode,
decode-batch frontend integration, Plot signal binding, Agent `dbc.*` tools, any new Python
endpoint, any new Runtime DBC domain model, any SQLite migration, any new `project.json`
field, any new Tauri command, and any Rust DBC parser. No TX, no real hardware work, no V0.4
capability.

The DBC **import** capability already exists (V0.3-06 / V0.3-07 / V0.3-08). It was
deliberately **not** wired into the workspace: this phase is read-only.

## 4. Architecture / boundary statement

```text
UI  ≠  CAN Runtime  ≠  Agent Runtime  ≠  Storage
```

- The DBC parser, semantic validation, decoding, persistence and integrity verification all
  remain the Python Runtime's authority. React re-implements none of them; it renders.
- All Runtime data is obtained through the already-accepted typed client
  (`src/runtime/dbc-client.ts`, V0.3-09). No new HTTP client, no second error taxonomy.
- `projectPath` remains an explicit argument. **No** global current project, **no** global
  active DBC, **no** channel ↔ DBC binding was introduced.
- Asset selection is UI-local component state. The tests prove it does not become a module
  singleton, and that changing `projectPath` clears it.
- The external DBC source path still cannot enter the renderer, the IPC payload or the HTTP
  contract: the read models carry no path and the renderer's filesystem capability was not
  expanded.
- DBC text (`name` / `comment` / `unit` / choice `label` / node `name`) is rendered as React
  text nodes. There is no `dangerouslySetInnerHTML` anywhere on this path.

### 7.2 Delivery-gate advisories (checked; false positives)

The delivery gate raised two YELLOW static-analysis advisories against
`DbcDatabaseView.tsx`. Both were checked against the code rather than accepted as stated,
and both are false positives:

- *"wrote-but-never-read: `estimateSize` / `getScrollElement` / `initialRect` / `overscan`"*.
  These are options of `useVirtualizer(...)`; they are read by `@tanstack/react-virtual`
  inside the library, not by this module. The identical option object is used by the
  pre-existing, already-accepted `apps/desktop/src/components/trace/TracePanel.tsx:22-25`.
- *"read-but-never-produced: `length`"*. The production write point is the typed client:
  `apps/desktop/src/runtime/dbc-client.ts:586` (message) and `:602` (signal) assign
  `length: readCount(record["length"], message)`. The advisory scoped its scan to the
  changed file and did not see the producer in the unchanged `dbc-client.ts`.

## 12. Known limitations and NOT VERIFIED items

- **Windowed desktop render of the DBC panel: NOT VERIFIED.** The MSI builds and the
  packaged Runtime smoke passes, but no windowed run was performed on this host to observe
  the DBC panel rendering inside the packaged application. The panel is proven by component
  tests and by the production bundle guard, not by a packaged visual run.
- **Dockview tab group placement under real mouse interaction: NOT VERIFIED.** The panel is
  asserted in the desktop layout by `App.test.tsx` (a `DBC` tab exists in the production
  workspace). Tab dragging / re-docking behaviour of the new panel was not exercised.
- **Virtualized message list with a very large real DBC: NOT VERIFIED.** Virtualization is
  structurally the one `TracePanel` uses and is unit-tested with a bounded window, but no
  multi-thousand-message document was rendered on this host.
- **`style_sheet`-level visual fidelity: NOT VERIFIED.** No design reference exists; the
  layout follows the existing Trace / Plot conventions.
- Pre-existing items still open and unchanged by this phase: real CAN hardware NOT VERIFIED;
  macOS NOT VERIFIED; near-limit Desktop HTTP serialization / renderer starvation (P2,
  unresolved); timestamp segment pruning still disabled; DBC registry-vs-filesystem
  non-atomicity; `dbc/`-as-symlink rejection skipped on Windows.
- No CI exists (`.github/` is absent), so every number above is a **local** run, not a CI
  result.
